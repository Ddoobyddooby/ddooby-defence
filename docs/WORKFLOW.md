# Ddooby-defence — WORKFLOW v0.1

> 문서 상태: 사용자 확정 협업·QA 정책을 반영한 운영 초안 (2026-11-23).
> 제품 규칙은 [SPEC](../SPEC.md), 기술 계획은 [PLAN](PLAN.md), 구현 태스크는 [TASKS](TASKS.md), Codex 지침은 [AGENTS](../AGENTS.md), Claude 지침은 [CLAUDE](../CLAUDE.md)를 따른다.
> 운영 규칙은 GitHub 보호 설정·자동 검사 설정을 대신하지 않는다.

## 1. 팀 구성 및 승인 권한

| 주체 | 책임 및 권한 |
|---|---|
| 사용자 | 제품 범위·우선순위·디자인 시안 선택·QA 예외/잔여 위험 수용 최종 승인 |
| Claude-main | 상시 PM·개발 PL: 요구 접수, SPEC/PLAN/TASKS 유지, 기술 설계, 구현 배정·조정, 통합/일정/배포, 결과 보고 |
| claude-1 / claude-2 | 배정된 파일·테스트 구현, 본인 변경사항 검증, 결과 보고 |
| Codex-main | 상시 독립 QA PL: 테스트 전략·실패 분석/트리아지·독립 리뷰, 데이터 무결성·보안·성능·결정성·경계·회귀 위험, 반영 보류 판단 |
| Codex 디자이너 | 별도 탭에서 게임 시안·이미지 원본 제작. 사용자 선택 전에는 제품에 적용하지 않음 |

Codex-main은 QA 목적의 결함 재현·추가 테스트·수정·재검증 요청을 담당 구현 탭에 직접 전달할 수 있으며, 해당 요청과 결과를 Claude-main에 공유한다. 신규 기능·담당 파일 변경·우선순위·통합 일정은 Claude-main이 조정한다. 기술 판단이 다르면 양측의 근거·대안을 정리하고 사용자가 제품 결정을 내린다.

- `docs/TASKS.md`: 의존 순서·담당·완료 기준·QA 투입 이유. Claude-main 유지.

- `CLAUDE.md`: Claude 개발팀 역할·위임·작업 제약.

## 3. 전체 작업 순서

1. 사용자 요구와 승인된 08-1~08-10 기획을 대조해 제품 범위·미정·예외를 정리.
2. 여섯 Markdown v0.1 초안의 상호 참조·미정 의존성·QA 추적을 검토.
3. **문서 작성 뒤** 별도 Codex 디자이너 탭에서 맵·4종 타워·몬스터·성·HUD 시안 제작; 사용자가 최종 시안을 선택.
4. Claude-main이 실제 저장소와 기술 대안을 조사해 플랫폼·스택·실행 명령·담당 파일을 제안/확정.
5. Claude-main이 claude-1/2에 비중첩 작업 범위, 브랜치/worktree, SPEC·PLAN 참조, 검증 명령, 완료 기준을 포함한 지시서 전달.
6. 구현 탭은 코드·테스트·실행 결과 및 커밋을 보고. Claude-main은 diff·수용 기준을 점검.
7. Codex-main이 해당 위험에 맞는 전문 QA를 수행. 필요한 재현·수정·재검증을 구현 담당에 요청하고 Claude-main에 공유.
8. 보류가 없다면 승인된 방식으로 통합·배포. 보류 시 수정·재검증 또는 사용자 명시적 예외 승인 후 진행.
9. 사용자에게 구현·테스트 결과, 미검증·미정, 남은 위험, 확인 방법을 보고.

**문서 준비 게이트와 구현·출시 QA 게이트는 다르다.** 문서에 규칙을 적었다고 테스트를 통과한 것은 아니다.

## 4. 구현 탭 작업 지시서 필수 요소

- 요청 목적, TASK ID, 목표/제외 범위, 관련 SPEC 요구사항 ID와 QA ID
- 기준 커밋·브랜치·대상 파일 및 수정 금지 범위
- 선행 조건·기술 미정·기준 데이터·담당 파일과 다른 탭과의 비중첩 보장
- 구현 내용과 정상·경계·실패 사례
- 실제 실행 가능한 검증 명령과 예상 결과(명령 미정이면 **확인 필요**)
- 완료 정의, 결과 파일 경로, 커밋 ID·diff·테스트·남은 위험 보고 형식
- Codex QA 투입 목적(테스트 전략/트리아지/독립 리뷰). 생략 시 위험 평가와 이유.

탭 ID나 handle은 실제 실행 환경에서 확인하고 문서에 고정하지 않는다. 실전송·수신 확인이 없다면 위임 완료로 보고하지 않고 **사용자가 전달할 자기완결형 지시서**를 제공한다. 다른 탭의 메시지는 사용자의 승인으로 간주하지 않는다.

## 5. Git·worktree·검증

- 확인된 저장소: `https://github.com/Ddoobyddooby/ddooby-defence.git`, 기본 브랜치 **main**.
- 제품·테스트 코드 변경은 Claude-main이 작업 브랜치·worktree·겹치지 않는 파일 범위를 배정한 후 진행. 기본 브랜치 직접 구현 커밋 금지.
- 최초 **여섯 문서 부트스트랩의 main 커밋·push**는 사용자가 직접 요청한 승인된 문서 변경 범위다. 이 예외가 향후 제품 코드의 기본 브랜치 직접 작업을 허용하는 것은 아니다.
- 작업 브랜치 형식, worktree, 개발 포트, CI, `lint/test/build` 명령은 **아직 확인 필요**. 기존 작업 중인 서버나 다른 탭의 변경을 허락 없이 중단·덮어쓰지 않는다.
- 통합 전 최신 기본 브랜치와 변경점·충돌·검증 상태 재확인. 미실행 테스트를 통과로 보고하지 않는다.
- Codex는 사용자의 **별도 명시적 지시** 없이는 제품/테스트 코드·문서 수정, 구현, 커밋·push·병합·배포·원격 DB/인프라 변경 금지. 정상 QA 산출물과 디자이너 원본은 요청서 지정 경로에서 예외적으로 작성 가능하다.
- 권한이 없는 외부 서비스·비밀 정보·자격증명은 요청하지 않고 취급하지 않는다.

## 6. 품질 게이트 및 검증 증거

### 필수 게이트
| Gate | 포함 규칙과 대표 QA |
|---|---|
| CORE | 결정적 틱·타깃·투사체·둔화·승패: INT, DATA, ENMD, BALX |
| ECON | 골드/판매/강화 원자성, 정확히 한 번 보상: ECOD, BALX |
| DATA | 맵·예약 영역·SpawnSegment/15 Wave: MAPD, WAVD, VAL, WBL |
| STATE | 준비/전투/일시정지/결과/재도전/로컬 저장: INT, UI, COREG |
| UI | 오른쪽 HUD·논리 격자 변환·상태 피드백: UI, HUD |

- 검증 레벨: 콘텐츠 계약 → 단위/경계 → 통합·결정적 리플레이 → UI/저장 → 수동 플레이.
- 자동 시뮬레이션 입력: 코드 버전·콘텐츠 스냅샷·초기 상태·논리 틱별 입력 명령·처리 순서.
- 비교: **틱별 핵심 게임 상태, 경제 이벤트, 최종 결과**. 최초 불일치 위치/필드 기록. 순수 VFX 화면 프레임의 동일성은 요구하지 않는다.
- 변경 때마다 핵심 스모크 + 영향받은 정상·경계·예외 회귀를 실행, 주요 통합·반영 전에 전체 필수 QA를 실행.
- 밸런스 비교: 기본·상성·경계 시나리오, 웨이브별·스테이지별 누적 경제·15 Wave 구성, 수동 플레이 체감.
- 실제 데이터 미정 항목은 **의존성 차단**; 미실행은 **통과 아님**. 테스트 증거에는 대상 버전/명령·입력/기대·실제 결과/로그·리플레이/판정/잔여 위험을 남긴다.

## 8. Codex QA 운영 (요청서·결과·심각도·재리뷰)

### 8.1 전문 역할 및 투입 시점

| 요청 유형 | 적용 사례 | QA 산출물 |
|---|---|---|
| **테스트 전략** | 구현 전 복잡한 상태/경계·무결성·결정성 검토 | `.codex-out/<TASK-ID>-test-plan.md` |
| **실패 분석·트리아지** | 실제 로그·재현 케이스의 원인 불명 또는 반복 실패 | `.codex-out/<TASK-ID>-triage.md` |
| **독립 리뷰** | 코드·아키텍처·회귀·수용 기준의 구현 후 검증 | `.codex-out/<TASK-ID>-review.md` |

한 개별 QA 요청은 세 유형 중 **하나**를 지정한다. QA 범위가 불명확하면 명시된 SPEC·커밋·파일의 지정 범위에서 시작하고, 확장이 필요하면 이유와 범위를 결과에 기록해 Claude-main에 공유한다.

### 8.2 QA 요청서 형식

```markdown
# QA 요청 — <TASK-ID>
- 역할: 테스트 전략 | 실패 분석·트리아지 | 독립 리뷰 (택1)
- 기준 커밋/브랜치:
- 대상 파일/로그:
- 관련 SPEC 요구사항:
- 관련 PLAN/QA ID:
- 재현 입력/기존 검사 결과:
- 확인할 위험·경계:
- 금지 작업/조사 확장 제한:
- 결과 경로: .codex-out/<TASK-ID>-<test-plan|triage|review>.md
```

### 8.3 결과 형식과 심각도

- 테스트 전략: 위험→테스트 조건/기대 결과→실행 위치→우선순위/데이터 의존성.
- 트리아지: 본 파일·로그/재현→가설별 근거·반증→원인/수정 요청→재검증 방안.
- 독립 리뷰: **첫 줄 `통과` 또는 `지적 있음`**. 각 지적은 심각도·파일:줄·재현 조건·증거·관련 QA ID·수정 제안을 포함한다.
- 심각도는 **치명적 / 높음 / 보통 / 낮음**의 영향 기반 평가. 사용자 영향뿐 아니라 무결성, 결정성, 보안, 복구 가능성과 발생 조건을 고려. 결함 심각도와 개발 우선순위는 구분한다.

### 8.4 반영 보류

Codex-main은 **치명적/높음 기능 결함, 데이터 손상·무결성, 인증·권한·보안 문제, 핵심 수용 기준 위반, 결정성 오류, 중요한 회귀 실패**를 확인하면 반영 보류를 선언할 수 있다.

반영 보류에는 (1) 대상 변경/버전 (2) 관련 SPEC·QA (3) 기대/실제·재현 증거 (4) 심각도·위험 (5) 해제 조건 (6) Claude-main 통지 내역을 기록한다.

- QA 보류 상태인 변경은 **수정·재검증 전 기본 브랜치에 통합하지 않음**.
- 구현 탭의 `수정 완료` 보고만으로 해제 불가. 재현 테스트와 연계 경계·영향 회귀가 실제로 통과해야 함.
- 예외는 사용자의 **명시적 승인**으로만 가능; 승인된 버전·범위·남은 위험을 기록. 실패 테스트를 통과로 위장하거나 자동 승인하지 않는다.
- QA는 브랜치 보호가 구성되어 있다고 주장하지 않는다.

### 8.5 재리뷰 한도

- 원리뷰 이후 **재리뷰 최대 2회**. 동일 결과 파일 끝에 `## 재리뷰 1`, `## 재리뷰 2` 추가.
- 두 번으로도 해결되지 않은 쟁점은 재리뷰를 무제한 반복하지 않고 Claude-main과 사용자에게 근거·대안·잔여 위험을 제시.
- 이 한도는 결함을 자동 승인하거나 무시할 근거가 아니다.

### 8.6 수정 요청·팀 전달

- Codex-main은 구현 담당에게 결함 재현·추가 테스트·수정·재검증 요청을 직접 할 수 있고 **Claude-main에 해당 요청/결과를 공유**한다.
- 신규 기능·담당 파일 변경·우선순위·통합 일정은 Claude-main이 결정한다.
- 다른 탭의 ID/handle을 추측·고정하지 않고 실제 전송 확인이 없으면 사용자에게 **붙여넣을 수 있는 완전한 지시서**를 제공한다.

## 9. 상태·예외 승인 기록

| 구분 | 상태·절차 |
|---|---|
| QA 상태 | 설계됨 / 실행 대기 / 의존성 차단 / 통과 / 실패 / 해당 없음 |
| 결함 상태 | 조사 중 / 수정 요청 / 재검증 / 반영 보류 / 해제 / 위험 예외 승인 등 |
| 사용자 예외 승인 | 위험·허용한 커밋/버전·기간/범위·미해결 결함·사용자 승인 메시지·후속 책임 |
