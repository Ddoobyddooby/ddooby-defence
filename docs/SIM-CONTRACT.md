# Ddooby-defence — 결정성 계약 (TECH-02, v0.1 초안)

> 상태: **claude-main 설계 초안, 2026-11-24.** 사용자 확인: 틱 20/초(50ms)·정수 고정소수점·비율 계산 반올림(2026-11-24). 코드 미구현, codex-main 테스트 전략 대기.
> 범위: SPEC 12절 **TBD-SIM**, PLAN 3.2·9절의 기술 계약 미정 항목. 게임 수치(공격력·속도·가격 등)는 정하지 않는다. 값이 아니라 **단위·연산·순서·식별자 규칙**을 정한다.
> 우선순위: SPEC > 이 문서 > PLAN. 이 문서가 SPEC의 확정 규칙과 충돌하면 SPEC을 따르고 이 문서를 고친다.

## 1. 원칙

- **같은 코드 버전 + 같은 콘텐츠 데이터 + 같은 초기 상태 + 같은 명령 기록 → 매 틱 같은 게임 상태·같은 경제 이벤트·같은 결과.** 브라우저·기기·프레임 속도가 달라도 같아야 한다.
- 게임 상태는 **정수만** 담는다(문자열 ID·불리언·`null` 허용, 소수 금지). 소수가 필요한 비율은 정수 단위(아래 3절)로 표현한다.
- 순수 코어(`src/game/core`)는 벽시계·난수·환경 의존 수학을 쓰지 않는다(6절).
- 렌더 프레임(Phaser)과 논리 틱은 분리한다. 렌더는 상태를 읽기만 하고 보간·VFX는 게임 결과에 영향을 주지 않는다.

## 2. 시간

| 항목 | 규칙 |
|---|---|
| 논리 틱 | **고정 50ms = 20틱/초** (`TICK_MS = 50`). 시뮬레이션 시각은 정수 틱 번호 `tick`(시도 시작 시 0)이다 |
| 콘텐츠 시간 단위 | 데이터의 모든 시간 값(준비 시간·Segment 시작·간격·둔화 지속·공격 주기·TTL)은 **정수 ms**로 쓰고 **50의 배수여야 한다**. 아니면 데이터 검증 오류(반올림 보정 없음) |
| 변환 | `ticks = ms / 50` (정확히 나누어떨어짐이 보장되므로 반올림 없음) |
| 시각 비교 | 모두 정수 틱 비교. "만료 시각" `expireTick = 적용 틱 + 지속 틱`. 만료 판정은 `tick >= expireTick` |
| 일시정지 | 틱을 진행하지 않는다. 일시정지 시간은 게임 상태·명령 기록에 나타나지 않는다 |

**벽시계 연결(Phaser 쪽, 코어 밖):** 프레임 경과 ms를 누적하고 50ms마다 `core.step()` 1회. 한 프레임 최대 5틱까지만 따라잡고 나머지 누적은 버린다(탭 비활성 복귀 시 폭주 방지). 이 정책은 게임 결과가 아니라 진행 속도에만 영향을 준다.

### 2.1 틱 안의 시점 정의

- SPEC 7절 8단계 순서를 그대로 따른다. 아래는 시점이 모호했던 부분의 정의다.
- **웨이브 시작 틱 `waveStartTick`:**
  - 조기 시작 명령이 틱 T의 1단계에서 적용되면 T.
  - 준비 타이머가 틱 T의 8단계에서 만료되면 T+1.
- **Segment 생성 틱** = `waveStartTick + (segment.startMs + i × segment.intervalMs) / 50`. 해당 틱 3단계에서 생성.
- **준비 타이머:** 준비 단계의 각 틱 8단계에서 1 감소, 0이 되면 전투로 전환(위 T+1 규칙).
- **둔화 적용:** 4단계 명중 시 `expireTick = tick + 지속 틱`. 이후 틱의 2단계에서 `tick >= expireTick`이면 제거.
- **공격 주기:** 타워는 `nextFireTick`을 가지며 4단계에서 `tick >= nextFireTick`이고 타깃이 있으면 발사, `nextFireTick = tick + 주기 틱`. 설치 직후 첫 발사 가능 틱은 SIM-02에서 정한다.

## 3. 숫자 단위와 연산

### 3.1 단위

| 양 | 단위 | 예 |
|---|---|---|
| 위치·거리·사거리·반경 | **밀리타일 `mt`** (1타일 = 1000mt). 타일 (col,row) 중심 = `(col×1000+500, row×1000+500)` | 사거리 2.5타일 = `2500` |
| 이동·투사체 속도 | 데이터: **mt/초**, 20의 배수 필수(아니면 검증 오류). 런타임: mt/틱 = 값/20 | `1000` mt/s = 50 mt/틱 |
| 비율(특성 배율·둔화·저항·환급률) | **bp(1/10000)**, 정수 | 25% = `2500` |
| 골드·HP·피해 | 정수 | — |
| 경로 진행도 `pathProgress` | 출발점부터 경로를 따라 이동한 mt | — |

### 3.2 정수 연산 규칙

- 모든 상태 정수는 `Number.isSafeInteger`이며, 데이터 검증기가 각 필드 상한을 둬서 중간 곱이 `2^53`을 넘지 않게 한다(상한 값은 DATA-01에서 정한다).
- **비율 적용 `applyBp(v, bp)` = 반올림(사용자 결정 2026-11-24).** 음이 아닌 정수 `v·bp`에 대해 `floor((v × bp + 5000) / 10000)` (0.5는 올림).
- **부호 있는 나눗셈 `roundDiv(a, b)`** (b>0): `sign(a) × floor((2|a| + b) / (2b))` (0에서 먼 쪽으로 반올림). 투사체·경로 보간에 사용.
- **정수 제곱근 `isqrt(n)`:** `floor(√n)`를 정수 보정으로 정확히 구한다(`Math.sqrt` 결과를 ±1 보정해 `r² ≤ n < (r+1)²` 보장).

### 3.3 규칙별 적용

| 규칙 | 계산 |
|---|---|
| 체력 강화 | `maxHp = max(1, applyBp(baseHp, 10000 + hpBoostBp))`, 생성 시 현재 HP = maxHp |
| 속도 강화 | `baseSpeed' = max(1, applyBp(baseSpeed, 10000 + speedBoostBp))` (둔화 전 기본 속도) |
| 실효 둔화 (SPEC 4절) | `effectiveSlowBp = applyBp(baseSlowBp, 10000 − controlResistanceBp)` |
| 둔화 적용 속도 | `speed = max(1, applyBp(baseSpeed', 10000 − 가장 강한 effectiveSlowBp))`. 둔화 bp 상한 < 10000은 데이터 검증 |
| **환급 (SPEC 8절 예외)** | `refund = floor(actuallyPaid × refundRateBp / 10000)` — SPEC 확정 규칙인 **내림 한 번**을 유지한다. 반올림 아님 |
| 사거리 판정 | `dx² + dy² ≤ range²` (정수, 제곱근 없음, 경계 포함) |
| 투사체 이동 | 남은 거리² ≤ 속도²이면 이번 틱 명중. 아니면 `d = isqrt(dx²+dy²)`, 위치 += `(roundDiv(dx×step, d), roundDiv(dy×step, d))` |
| 경로 위 위치 | waypoint 구간에서 `pathProgress`로 선형 보간(`roundDiv`). 판정·정렬에는 `pathProgress`(정수)를 쓰고 보간 좌표는 사거리 판정에만 쓴다 |

## 4. 명령

- 모든 플레이어 행동(HUD·맵 클릭)은 같은 경로로 코어에 `Command`를 넣는다: `build`, `upgrade`, `sell`, `setTargeting`, `startWave`(조기 시작).
- 코어는 접수 시 시도 안에서 단조 증가하는 **`seq`(1부터)**를 붙인다. 접수된 명령은 **다음 틱의 1단계에서 `seq` 오름차순**으로 적용한다.
- 각 명령은 **앞 명령까지 반영된 상태**로 재검증한다. 예: 골드 100에서 설치 60 명령 두 개가 같은 틱이면 첫째 성공, 둘째는 골드 부족으로 거부.
- 거부된 명령은 상태를 바꾸지 않고 `commandRejected{seq, reason}` 이벤트만 남긴다.
- 일시정지·결과 단계에 들어온 게임플레이 명령은 **접수 시 즉시 거부**(seq 미부여, 기록에 남지 않음). SPEC 8절 "무허용 경제 명령 거부".
- 판매 확인창 취소 같은 UI 상태는 코어 밖이다. 코어는 `sell` 적용 시점의 단계·타워 존재만 재검증한다.
- 스테이지 선택·재도전은 시도 밖 명령으로 새 시도를 만든다(5절).

## 5. 식별자·이벤트 키

| 대상 | 규칙 |
|---|---|
| `attemptId` | 세션 안에서 새 시도(진입·재도전)마다 1씩 증가. 저장하지 않는다. 난수·시각 사용 안 함 |
| `towerId`·`projectileId`·`enemyId`·`commandSeq`·`eventSeq` | 시도마다 1부터 시작하는 정수 카운터. 재도전 시 초기화 |
| 적 ID 부여 순서 | 3단계 생성 시 `(생성 틱, Segment 원본 순서, Segment 내 순번)` 오름차순으로 부여. 따라서 `spawnSerial == enemyId`이고 SPEC의 "생성 순번 → 적 ID" 동률 규칙과 일치 |
| 경제 이벤트 키 | `kill:e{enemyId}`, `waveClear:w{waveIndex}`, `build:c{seq}`, `upgrade:c{seq}`, `sell:t{towerId}`. 시도 상태에 `consumedEconomyEvents`(키 집합)를 두고 이미 있으면 정산하지 않는다(정확히 한 번). 로그·리플레이 출력에는 `a{attemptId}:` 접두어를 붙인다 |
| 경제 원장 | 시도별 추가 전용 목록 `{tick, eventSeq, key, delta, goldAfter}` |

## 6. 순회 순서·금지 사항

- 4단계 타워 발사: `towerId` 오름차순. 투사체 처리: `projectileId` 오름차순. 6단계 적 이동·기지 도달: `enemyId` 오름차순. 이벤트는 발생 순서대로 `eventSeq`를 붙인다.
- 상태 컬렉션은 ID 오름차순 배열(또는 그 순서로만 순회되는 구조)로 보관한다.
- **코어 금지:** `Math.random`, `Date`, `performance`, `Math.sin/cos/tan/atan2/pow/exp/log/hypot`, 상태 안의 소수. ESLint `no-restricted-properties`/`no-restricted-globals`로 강제(구현 태스크에서 추가).

## 7. 직렬화·해시·리플레이

- **정규 스냅샷:** 시도 상태를 키 정렬된 JSON으로 만든다. 배열은 ID 순, 값은 정수·문자열·불리언·`null`만. 정수가 아닌 숫자가 있으면 예외를 던진다(결정성 위반 조기 발견).
- **틱 해시:** 정규 스냅샷 문자열 + 그 틱의 이벤트 목록을 FNV-1a 64비트(`BigInt`)로 해시해 16진수 문자열로 둔다. 보안 목적 아님.
- **리플레이 기록:** `{codeVersion, contentHash, stageId, commands: [{tick, seq, kind, payload}]}`. `contentHash`는 해당 스테이지 콘텐츠 데이터 정규 JSON의 FNV-1a 64 해시.
- **리플레이 검증:** 같은 기록을 두 번 실행(또는 기록 재생 vs 원 실행)해 틱별 해시를 비교한다. 다르면 **첫 불일치 틱**에서 두 스냅샷을 필드 경로 단위로 비교해 출력한다. 순수 VFX는 비교 대상 아님(CLAUDE.md 4절).

## 8. 이 계약에서 정하지 않는 것

- 게임 수치 전부(TBD-TOWER/ENEMY/ECON/WAVE/PROJECTILE), 각 필드 상한 값 → DATA-01 및 사용자 승인.
- 같은 틱에 이미 HP 0이 된 적에게 다른 투사체가 명중하는 경우, 설치 직후 첫 발사 틱 → SIM-02.
- 경로 폭·대각 구간 허용 여부·격자 경계 클릭 귀속 → MAP-01.

## 9. 완료 증거 (TASKS TECH-02)

이 문서 승인 후, 순수 코어에 다음 기초 모듈과 테스트를 구현한다(구현 담당 배정은 claude-main).
- 시간 변환·검증(`ms → ticks`, 50 배수 검사), `applyBp`·`roundDiv`·`isqrt`, 시도별 ID 카운터, 명령 큐(seq 부여·정렬·순차 재검증), 정규 스냅샷·FNV-1a 64 해시, ESLint 금지 규칙.
- 결정성 테스트: 최소 장난감 시뮬레이션(명령 큐 + 카운터 + 해시)으로 같은 기록 2회 실행 시 틱별 해시 동일, 명령 하나를 바꾸면 해당 틱부터 불일치 및 첫 불일치 틱 보고.
- 테스트 케이스 목록은 codex-main 테스트 전략(`.codex-out/TECH-02-test-strategy.md`)을 따른다.
