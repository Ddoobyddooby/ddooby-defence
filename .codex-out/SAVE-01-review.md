## F1 — 높음: 일시적 읽기 예외 뒤 새 클리어가 기존 정상 기록을 덮어씀

- 위치: `src/game/session/progress.ts:94`·`:95`(읽기 실패 뒤 빈 메모리), `:135`·`:139`(다음 쓰기에서 재확인 없이 본 키 교체).
- 재현: 백엔드 본 키에 `{"version":1,"cleared":["stage-1"]}` 저장. 첫 `getItem`만 예외(일시적 저장소 접근 실패) → `load()="unavailable"`, 메모리 `[]`. 읽기가 복구된 뒤 `markCleared("stage-2")` 실행.
- 기대: 세션의 새 클리어는 메모리에 남되, 기존 키를 읽지 못한 상태에서 stage-1을 잃지 않도록 저장을 보류하거나 복구 시 병합.
- 실제: `markCleared="saved"`, 본 키가 `{"version":1,"cleared":["stage-2"]}`로 바뀌어 기존 stage-1이 소실. 테스트 백엔드의 getItem 실패와 setItem 성공을 분리해 직접 확인.
- 영향: 새로고침 이후 이미 획득한 클리어가 사라지고 잠긴 스테이지가 다시 생긴다. SPEC 10절의 기존 클리어 유지 및 실패·재시도 의도 위반.
- 수정 제안: 읽기 성공 여부를 추적하고 `unavailable` 이후 본 키 쓰기 전에 재읽기·유효 데이터 병합을 요구. 재읽기가 계속 실패하면 메모리 클리어는 유지하되 쓰기를 failed로 두고 재시도 경로 제공. 기존 정상 기록이 있던 경우와 실제 빈 키인 경우를 구분하는 회귀 테스트 추가.

## F2 — 높음: 손상 원문 백업 실패 뒤 첫 저장이 유일한 원문을 삭제

- 위치: `src/game/session/progress.ts:100`·`:108`·`:112`(백업 실패를 무시), `:139`(본 키 덮어쓰기).
- 재현: 본 키에 `{"version":2,"cleared":["old-stage"]}` 저장. `PROGRESS_CORRUPT_KEY`의 `setItem`만 한 번 예외 → `load()="unreadable"`, corrupt 키 없음, 본 키 원문 유지. 예외 복구 후 `markCleared("stage-1")`.
- 기대: 읽지 못한 원문을 corrupt 키로 보존한 후 본 키를 교체하거나, 보존할 수 없으면 교체를 막고 재시도 안내.
- 실제: `markCleared="saved"`, 본 키 `{"version":1,"cleared":["stage-1"]}`, corrupt 키 없음. 이전 원문은 어느 키에도 남지 않음. 직접 재현.
- 영향: 버전 변경/손상 파일의 수동 복구 가능성이 사라진다. UI-CONTRACT 10절의 “덮어쓰지 않고 원문을 corrupt 키로 옮겨 둔 뒤” 조건 위반.
- 수정 제안: 백업 성공 상태를 추적하고 첫 저장 및 retrySave 전 미보존 원문을 다시 백업. 실패 중에는 기존 키를 덮어쓰지 않고 저장 상태 failed로 표시. 손상 원문 보존 실패 → 쓰기 복구 조건을 독립 테스트.
- 추가 경계: corrupt 키에 이미 다른 원문이 있으면 새 손상 원문은 현재 구현에서 복사되지 않는다. 이번 계약의 “한 번” 정책 해석상 두 번째 원문 보존 여부는 명시가 필요하다. 적어도 현재 본 키를 교체하기 전, 새 원문을 보존하지 않는다는 위험을 결정·문서화해야 한다.

## 확인된 동작과 검증 한계

- 세션 승리 시 `markCleared`가 메모리에 즉시 반영돼 저장 실패 중에도 세션 해금이 유지된다. 패배·재도전·스테이지 전환은 기록을 삭제하지 않는다. 다음 클리어 저장과 `retrySave`는 현재 메모리의 전체 클리어 목록을 쓴다. 같은 스테이지 재클리어에서 상태 saved면 쓰기를 생략하고 failed면 다시 시도한다.
- 저장 상태는 store 전체의 마지막 쓰기 상태지만 한 번의 성공한 쓰기가 현재 메모리 전체를 담으므로, Stage 1 실패 후 Stage 2 성공 시 Stage 1까지 저장됐다는 의미에서 saved 표시는 섞임으로 보지 않는다.
- 모르는 문자열 stageId는 보존하고, 비문자열 항목은 제거한다. `browserStorageBackend`는 window 없는 서버에서 null을 반환하며 접근 예외를 잡는다. StrictMode의 별도 생성 두 번은 corrupt 키가 이미 있으면 추가 쓰기를 하지 않는 경로를 코드로 확인했다. 실제 브라우저 hydration·Android 앱 저장소 동작은 직접 실행하지 않았다.
- 640×320 실패 결과 스크린샷은 **패딩 축소 전** 촬영본으로 패널 상하 여백이 약 3~4px이다. 현재 `p-3` 변경은 높이를 줄이는 방향이지만, 변경 후 재촬영이 없어 실제 결과 오버레이 무넘침은 **미검증**. claude-main/claude-1의 브라우저 확인 및 APK 빌드는 보고 근거로만 취급한다.
