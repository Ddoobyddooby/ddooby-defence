## 지적

### F1 (보통) 탭 복귀·rAF 정지 직후 첫 프레임에 경과 시간 전체가 세션으로 들어가 5틱이 한 번에 실행된다
- 위치: `src/game/phaser/scene.ts:119-121`(`delta = time - lastTime`, `session.advance(delta)`), `src/game/ui/GameApp.tsx:56`(`setHidden`), `src/game/session/session.ts:195-198`.
- 근거: 계약 UI-CONTRACT 5절은 "숨김 → 보임 복귀 시 누적은 0부터 시작"이다. `setHidden(false)`는 `acc`만 0으로 만들 뿐이다. 씬의 `lastTime`은 숨김 이전 프레임 값이라, 복귀 후 첫 `update(time)`의 `delta`가 숨김 시간 전체(수 초~수 분)가 된다. 이 시점엔 `hidden=false`이므로 `advance(huge)`가 5틱을 실행하고 나머지를 버린다. 결과: 복귀 순간 게임이 0.25초치 한꺼번에 진행된다(폭주는 5틱 상한이 막지만 "0부터"는 아님).
- 재현(모사: rAF 보류 + `document.hidden`/`visibilitychange` 모의, 6초): 같은 방식의 대조 실험에서 복귀 후 준비 남은 시간이 `18.6 → 18.4(60ms) → 18.3(120ms)`로 줄었고, 숨김 없이 120ms 관찰한 대조는 `19 → 18.9`였다. 즉 120ms 동안 약 0.3초가 줄어 5틱(0.25초) 점프와 일치한다. 실제 탭 숨김에서는 Phaser가 루프를 멈췄다 재개하므로 같은 경로를 탈 가능성이 높지만 **실제 탭 숨김으로는 검증하지 못했다.**
- 단위 테스트가 못 잡는 이유: `session.test.ts:118`은 세션 내부만 본다. 씬의 `lastTime`·delta 계산은 테스트 범위 밖이다.
- 수정 제안: 씬에서 `delta`를 상한(예: `Math.min(delta, 100)`)으로 제한하거나, `visibilitychange` visible 때 씬의 `lastTime = null`로 리셋(또는 세션이 "복귀 후 첫 advance 입력 무시" 플래그를 가짐). 세션 쪽에서 막는 편이 단위 테스트가 쉽다(`setHidden(false)` 직후 첫 `advance(10000)`이 0틱임을 단언).

### F6 (낮음) 같은 명령을 틱 사이에 두 번 보낼 수 있고 두 번째 거부 문구가 뜬다

- 수정 제안: 세션이 제출 후 해당 버튼을 다음 틱까지 비활성화하거나 같은 종류의 대기 명령을 합친다(표시 문제만).

### F7 (낮음) 캔버스가 devicePixelRatio를 반영하지 않아 고해상도 화면에서 흐리다
- 실측: DPR 2에서 `canvas.width = 1192`, CSS 폭도 1192(내부 해상도 = CSS 해상도). 좌표 변환은 정확하다(칸 (5,1) 클릭 좌표 (365,161)에 타워가 그려짐을 스크린샷으로 확인). 자리표시 도형이라 지금은 영향이 작으나 모바일에서 눈에 띌 수 있다.
- 수정 제안: 후속 아트 교체 때 `resolution`/스케일 정책을 함께 결정.

### F8 (낮음, 테스트 범위) 브라우저 전용 코드 무검증
- `scene.update` 시간 계산(F1), `areaPoint`·`syncSize`·`relayout`은 단위 테스트가 없다. 레이아웃·좌표(`cellAtAreaPoint`)·세션 시간은 리터럴 기대값으로 충분히 검증됨(기대값이 구현 helper를 재사용하지 않음을 확인). 시간 변환을 순수 함수(예: `frameDelta(time, lastTime, hidden)`)로 빼면 F1을 테스트로 고정할 수 있다.

### N1 (확인 필요) 실제 휴대폰 가로 화면의 `innerHeight`
- 주소창이 보이는 휴대폰 가로 모드는 `innerHeight`가 360 미만인 경우가 흔하다. 그러면 `tooSmall` 안내가 뜬다. 계약의 최소 크기 결정(800×360) 자체는 지켜지지만, 실제 기기에서 플레이 가능한지는 미검증이다(claude-1 보고 (f)와 같은 범위).
- 부가: HUD 버튼에 `touch-action: manipulation`이 없어 iOS에서 빠른 더블탭 확대가 날 수 있다(미확인).

### 요청한 점검 결과

1. **skipNextAdvance 경로:** 플래그는 `hidden→visible` 전환에서만 켜지고(`!hidden && this.hidden`), 숨김 중 `advance`는 그 앞에서 0을 반환해 플래그가 보존됨. 일시정지 중 숨김→복귀는 첫 입력만 버려지고 `acc=0`, 재개 후 정상. 결과 단계·스테이지 선택 중 켜진 플래그는 다음 첫 `advance`(씬 첫 프레임 `delta=0`)에서 소모되어 영향 없음. 재도전·세션 교체는 Battle만 교체하고 플래그는 세션 속성이라, 복귀 직후 재도전하면 첫 프레임 1회만 버려지며 무해(최대 한 프레임 분). 단위 테스트가 큰 값 10000ms·연속 `setHidden(true)`·숨김이 아닐 때의 `setHidden(false)`를 고정. 잘못 버리거나 남기는 경로 없음.
2. **pending:** `pending`은 `Battle` 객체 소속이라 재도전·스테이지 전환·`toStageSelect`로 세션이 바뀌면 함께 폐기됨(영구 비활성 경로 없음). 일시정지 중에는 게이트가 막아 새 pending이 생기지 않고, 일시정지 전에 제출한 pending은 재개 후 첫 step에서 해제(테스트 있음). "명령은 다음 step에 적용"은 SIM-CONTRACT 2.1(접수 시 `applyTick = completedTick + 1`, 1단계에서 소비)과 일치. `b.pending.clear()`가 `core.step()` 호출 뒤에 있어 step이 예외를 던지면 pending이 남지만, 그 경우 명령도 큐에 남아 있고 같은 예외가 계속되는 치명 상태라 의미 있는 새 경로가 아님(참고).
3. **F2 자동 일시정지:** 결과 단계는 `pause()`가 `isResult()`에서 조기 반환(코어 오류 안 감), 준비 단계도 일시정지됨, 전투 없음(스테이지 선택)은 no-op. 문서는 "진행 중 전투"라고 쓰지만 코드는 준비 단계도 일시정지한다(무해, 문구 불일치만).
4. **회귀:** 기존 테스트 의미 약화 없음. 변경된 기대값은 포맷 변경(`0.80`, `2.00초`)과 복귀 직후 첫 입력 폐기뿐이며 원래 의도(복귀 시 누적 0)를 더 엄격하게 고정. 하드코딩 재도입 없음.
